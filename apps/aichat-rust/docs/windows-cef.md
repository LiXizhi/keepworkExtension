# Windows CEF 兼容启动

Windows 兼容启动方案用于处理 WebView2 不可用的机器，包括 Windows 7 / 8。它提供一个能在旧系统运行的原生启动器，在启动现代 Rust / Tauri 程序之前选择宿主。CEF 不是 Tauri 2 中可动态加载的 DLL 插件，必须连同针对该 CEF 版本编译的宿主一起发布。本文同时记录历史通用兼容预览和独立 Win7/Win8 x64 专版，两者的安装包与 MCP 范围不同。

这是一条单独的兼容构建路径。现有 Windows Tauri 安装包及 macOS / Linux 路径继续使用原来的 WebView。历史通用兼容安装包不内置 CEF；首次进入该 CEF 路径需要联网下载完整宿主包，之后使用经过验证的本地缓存。独立 Win7/Win8 专版默认构建内置已签名 CEF109 归档的完整包，也保留按需下载的薄包，区别见下节。

**验证状态：兼容预览，尚未完成 Win7/Win8/Win8.1 虚拟机或实机验收。** `0.2.44` 引入的是通用 CEF 预览；后续增加独立 Win7/Win8 专版的实现和打包路径。源码/fixture 检查、现代 Windows 上的编译、每个旧系统上的实际运行和 CDN 发布必须分别记录，不能相互替代。用户已于 2026-11-14 授权跳过三系统实测直接发布 CDN；每次发布记录绑定产物的豁免，保持 `nativeLegacyVerified: false`。地址是否在线以当次发布回执为准，具体流程见 rust-release Skill。

## Win7/Win8 x64 专版契约

专版覆盖 **Windows 7 SP1 x64、Windows 8 x64、Windows 8.1 x64**，三者分别验收。使用原生 C++ `Keepwork.exe` 启动器、legacy CEF 109，以及从共享 `apps/mcp-rust` 源码构建的 Win7/Win8 专用 MCP。安装目录为当前用户的 `%LOCALAPPDATA%\Programs\KeepworkWin7Win8`，安装包名为 `Keepwork_Win7_Win8_<version>_x64-setup.exe`，不包含也不尝试启动现代 Tauri EXE。安装后创建当前用户的桌面快捷方式「Keepwork Windows 7 and 8」，以及原有开始菜单入口；它们都通过安装目录中的 `Keepwork.exe` 启动，卸载时清理对应快捷方式。

| 专版形式 | 打包输入 | 首次启动 CEF |
| --- | --- | --- |
| 完整包，预览工作流默认 | `build-win7.cjs` / `package-win7.cjs` 传 `--cef <已签名 CEF release-dir>`，内置匹配信任根的 CEF109 归档，安装体积较大 | 无已验证 active 缓存，或内置宿主版本更高时，校验并解包内置归档，不要求 CEF CDN 已发布 |
| 薄包，可选 | 不传 `--cef`，仅安装 Launcher 和兼容版 MCP | 无可用缓存时从 legacy 签名 feed 下载完整宿主包，需要网络和可用 CDN |

两种形式均对 CEF 清单验签并检查归档大小、SHA-256 和路径安全；已有已验证缓存继续按缓存策略使用。客户端升级若带来同通道、同架构且符合系统下限的更高版本内置宿主，会尝试使用该宿主；同版或更旧的内置宿主不替换已有 active。候选保存在新的摘要目录中，原生就绪确认后才更新 active，不原地覆盖旧缓存。`--update-cef` 仍从独立签名 feed 检查更新。内置 CEF 不表示允许混用任意 DLL，也不代表云聊天可离线使用。预览可在没有已发布 CDN 的条件下验证内核启动；安装、CEF 渲染与真实账号登录仍未经过逐系统实测，按 Skill 授权发布不代表这些能力已验证通过。

启动器尝试启动或附着本机 Rust MCP；MCP 缺失、启动失败或端口已被其他进程占用，均不能阻止云聊天窗口打开。从 `0.2.146` 起，CEF 仅为受信任的 AIChat 主页面注入宠物文字专用的 `window.aichatDesktop` 子集，不提供完整桌面 Bridge。文件与终端能力仍通过现有 loopback HTTP/MCP 协议发现和协商，依服务能力使用基础文件、目录、搜索、`grep_files` 和 `run_terminal`；兼容宿主不代替网页的用户确认，也不放宽路径、Origin 或认证检查。

启动失败时，启动器在打开聊天窗口后显示原因与日志目录。专版的诊断保存在 `%LOCALAPPDATA%\KeepworkWin7Win8\mcp-startup-error.txt`；尝试创建服务进程时，将其标准输出和错误写入同目录的 `mcp-runtime.log`。进程创建失败保留 Windows 错误码，提前退出保留退出码；日志用于定位失败，不能从聊天窗口已打开推断 MCP 已启动。

专版的日常文件浏览不要求用户升级 Win7 自带的 PowerShell 2。`/fs/locations` 通过原生 Windows Known Folder 查询读取系统配置的 Desktop、Documents、Downloads、Pictures、Music 和 Videos，保留重定向及本地化后的实际路径，不硬编码用户目录下的英文子目录。位置发现只返回已存在的可用目录，不创建文件夹；单位置查询失败不阻断其他位置、Home、盘符或普通目录浏览，既有响应字段和位置 ID 保持兼容。构建机上使用现代 PowerShell 与此最终用户依赖边界分开。

专版初始 MCP（包括 `0.2.66`）不提供交互式 PTY。从独立 MCP `0.2.67` 起，完整专版运行时打包固定来源的 WinPTY `0.4.3` x64 `winpty.dll`、`winpty-agent.exe` 及许可证，通过现有 HTTP `pty-session-v1` 提供真实交互式 shell、输入、输出续流、尺寸调整、打断和关闭，不依赖 Node 或现代 ConPTY。只有相邻依赖文件通过摘要核验、DLL 成功加载且后端就绪探测通过时，健康端点和能力通知才广告 `terminalApi`；首次探测创建并释放 WinPTY 后端，不启动用户 shell 或执行命令。依赖缺失、损坏、加载或就绪失败时不广告，终端路由返回 HTTP `501` / `UNSUPPORTED_FEATURE`，普通聊天、文件操作和非交互式 `run_terminal` 继续可用。`run_terminal` 的 `cmd.exe /c` 执行不能宣称为 PTY 的等价回退。

MCP `0.2.68` 将后端就绪探测放到后台，并修复首次启动超时被永久记为不可用的问题。单次探测和自动重试均有界，并发健康请求复用同一探测，不启动用户 shell；短暂启动失败可在同一进程恢复，依赖摘要或加载错误仍拒绝使用，修复依赖后需重新启动服务。健康响应新增可选 `terminalStatus`（`initializing`、`ready`、`unavailable`）和失败时的 `terminalReason`；原因使用固定有界文案，不包含本机路径或底层错误内容。只有 `ready` 才返回既有 `terminalApi: "pty-session-v1"`。每 25 秒的 SSE 心跳重新读取实际健康能力，使旧网页也能发现后台恢复；缺失或未知诊断字段表示状态未知，不要求客户端与 MCP 版本相同。

从桌面 `0.2.148` 起仍按当前连接服务的实际能力启用网页终端入口；附着旧 `0.2.66` daemon 时终端灰显符合预期，不按版本号伪造能力，也不为启用终端结束其他应用拥有的 MCP。灰色截图本身不能区分旧服务、启动未就绪、依赖失败或连接问题，应核对实际 `/health` 的 `runtimeVersion`、`terminalApi` 和可选诊断字段。终端保留 Origin、认证、会话归属、并发限制、30 分钟空闲清理和输出游标规则；相对 `cwd` 拒绝 `..` 段，并核对存在祖先的真实路径，不能因末级目录尚不存在或 canonicalize 失败而绕过工作区约束，已有绝对 / `~` 目录的允许语义保持。断流后不自动重放输入，关闭终端只清理该会话，不结束共享 daemon。真实 Win7/Win8/Win8.1 上的 WinPTY 启动、中文输入输出及交互仍待分别验收。

从旧兼容版升级后，若现有服务仍为 `0.2.66`，先完成其他 AIChat 客户端的任务，再打开「本地 MCP 面板」，核对当前服务并主动确认 `Stop service`；这会断开已连接客户端并结束该服务中的运行工作，不能将其理解为无中断热更新。停止完成后，在原生帮助菜单或托盘选择「启动本地服务」，随后重新打开网页「＋」菜单探测能力。新启动入口仅以本机传入的绝对 `Keepwork.exe` 路径执行固定 `--start-mcp`，无需关闭或刷新当前 CEF 页面，保留网页草稿；宿主没有有效启动器参数时隐藏此入口。`--start-mcp` 在既有启动器锁内只尝试启动 / 附着已验证运行时，已有任何可用 Keepwork 服务时继续附着，不停止或替换它，也不另占端口。服务由其他产品管理时，应由用户在相应管理入口完成操作；启动本地服务不是自动重启或通用命令执行权限。

支持原生重启契约的兼容版在帮助菜单和托盘提供「重启本地 MCP」入口，可直接完成本专版旧后台到已验证运行时的切换，不再要求用户先去面板停止服务。发现本专版管理的活动服务时，先一次性说明正在执行的本地任务和终端会中断，用户确认后才停止；取消不改变现有服务、网页或草稿。宿主保持打开，操作不刷新页面，也不重放未确认结果的命令或终端输入。服务启动后仍依健康响应的真实 `terminalApi` 启用终端，不能仅凭重启成功或版本号点亮菜单。

可重启归属同时依赖 Keepwork 健康身份、本专版的管理标记、有效 PID 和操作系统查询到的实际受管可执行文件路径；仅凭 HTTP 自报管理应用不足以取得停止权限。执行前重新核对当前服务与已打开的进程句柄，实例或路径变化时停止操作。其他产品管理的服务、未知占用、无有效 PID 或无法核验路径的进程保留原样，并提示到相应管理应用操作；没有服务时启动已验证候选，不按进程名批量结束进程或启用第二个端口。历史 `--start-mcp` 继续只有启动 / 附着语义。

桌面 `0.2.149` 的「启动本地服务」在启动或附着后显示只读健康结果，包括服务提供的实际版本和终端已就绪、初始化中或不可用的状态。服务没有广告终端能力且没有已知诊断状态时，明确显示「当前服务未声明交互终端能力」，不凭版本号断言原因；若需要人工切换服务，提示先完成已连接客户端的任务再主动停服。该反馈不结束或替换当前 peer，不新增网页 API，不刷新页面或改动草稿。

未安装 SP1 的 Win7、32 位系统、ARM64，以及完整桌面 Bridge、本地模型、蓝牙语音遥控和现代 AI CLI / 消息渠道的完整兼容，均不在首版承诺范围。`0.2.142` 增加原生系统托盘核心操作，`0.2.143` 增加标题栏主题跟随和简版桌面宠物，`0.2.144` 对齐原生标题栏布局及悬停交互，`0.2.146` 增加下述宠物文字对话子集；它们不表示现代桌面端的全部功能已移植。

MCP 继续只监听 `127.0.0.1:8089`，遵守单 daemon 和进程归属保护。已有可用 daemon 时按其真实能力使用；不因版本、架构或 Win7/Win8 标记不同就结束现有进程，不占用其他端口绕过单实例，也不把未知进程识别为可接管实例。不得把另一台机器上的 MCP 当成本机服务而放开 LAN 监听。

专版与现代版的发行及更新身份分别维护：

| 产物 | 专版身份 / 地址 | 约束 |
| --- | --- | --- |
| Win7/Win8 客户端 | `https://cdn.keepwork.com/keepwork/aichat-rust-win7-win8` | 安装目录 `KeepworkWin7Win8`；不得消费现代 Tauri 安装包 feed |
| Win7/Win8 Rust MCP | `https://cdn.keepwork.com/keepwork/mcp-win7-win8-rs` | `windows-x64`，`variant: "win7-win8"`，明确 `minWindows`；不能以普通 Windows MCP 包替换 |
| CEF 109 | `https://cdn.keepwork.com/keepwork/aichat-cef/v1/legacy/windows-x64/stable.json` | 继续使用独立签名清单和匹配的宿主/DLL，不替换为现代 CEF |

版本号仍按桌面和 MCP 两产品独立递增，协议能力依实际实现协商。先校验相应签名、大小、SHA-256 和产物身份，MCP 另核对其编译来源，再切换候选；失败保留已验证缓存，不自动重放结果不明的文件写入或终端操作。客户端安装包、独立 MCP 包和 CEF 包是不同产物，完成其中一种构建不表示另外两种已发布。

专版显式更新入口为 `Keepwork.exe --update-mcp`、`--update-client`，CEF 继续使用 `--update-cef`。MCP 更新验签并下载至暂存区，已有 daemon 继续运行，待下次服务启动健康检查通过才激活；不因下载完成结束现有进程。若 pending 候选启动失败，移至 `failed.json` 隔离，并可重新验签、校验先前保存的另一份 active 后尝试启动；不重放终端或文件任务。没有可用旧 active、旧版本同样失败或其他进程占用端口时，保留数据并继续云聊天，不能保证本地服务自动恢复成功。

客户端在启动后约 15 秒检查专版签名 feed，此后约每 6 小时检查一次；帮助菜单和托盘的「检查更新」可立即发起同一流程。发现更新后后台下载并校验安装器，原生进度窗口与摘要分别显示检查、下载、已就绪和失败状态，当前版本与候选版本保持独立。下载完成后通过托盘提示，并提供「退出并更新」或稍后；后台检查及下载不关闭页面，不强制安装，也不因普通关闭、`Alt+F4`、隐藏到托盘或普通完全退出而开始安装。

用户选择「退出并更新」后，重新核验确认时的同一候选，再请求 CEF 正常退出；页面取消退出时保留原窗口、草稿与已下载候选，不启动安装器。宿主完成退出后才交给已验证的安装器，避免安装目录仍被使用。检查、下载、重启和安装操作串行去重，重复点击不能启动多个安装器。客户端升级不结束独立 MCP，不清理聊天 profile，也不宣称安装器具备原子回滚。

客户端清单、下载大小与摘要、缓存和安装前的复核继续限定在 Win7/Win8 x64 专版渠道；错误签名、错误架构、错误系统下限、降级及同版本不同摘要均不能进入安装。客户端更新独立编译固定的官方 `keys/win7-release-public.pem` 公钥，其 `common/client_update_key.hpp` 必须与该 PEM 一致；本地预览的 CEF/MCP 组件仍使用各包隔离签名，不把预览私钥或 feed 提供的任意公钥加入客户端更新信任。离线或新候选下载失败时保留之前已验证的候选和上次检查信息，明确标示过期状态，不把旧候选冒充新版本。MCP 与 CEF 仍使用各自独立的签名 feed 和暂存 / 激活规则；软件自动更新不等于同时重启 MCP 或替换运行中的 CEF。

新增的原生重启和更新操作分别协商可选宿主 / 启动器能力；缺失或未知能力仅隐藏对应入口，历史签名宿主与启动器仍可聊天、启动服务和使用现有操作。不通过客户端或 MCP 版本号猜测支持，不给只支持 `--start-mcp` 的旧启动器发送新命令。原生菜单只调用固定本机操作，不新增网页更新、任意进程执行或通用文件权限。

专版构建和打包使用独立入口：`apps/mcp-rust/scripts/build-win7.cjs`、`package-win7-runtime.cjs`，以及 `apps/aichat-rust/scripts/build-win7.cjs`、`package-win7.cjs`。技术路径中的 `win7` 和 Rust 目标 `x86_64-win7-windows-msvc` 表示最低系统兼容目标，对外产品标识统一为 `win7-win8`，不是单系统发行承诺。详细操作按 [rust-release 的 Win7/Win8 参考流程](../../../.github/skills/rust-release/references/windows7.md) 执行；默认 `all` 包含专版，`modern` 和 `mcp-server` 明确排除专版。远端构建沿用唯一桌面主工作流 `aichat-rust-windows-release.yml`：默认 `edition=all` 同时构建现代版与专版，仅专版时选择 `edition=win7-win8`。正式发布须显式选择 `legacy-signing=production`，并提供真实三系统验收或用户授权的当次 `--native-acceptance-waiver`；不能以预览签名或现代 MCP 的 deferred 模式替代。`aichat-rust-win7.yml` 仅作为主工作流调用的可复用实现，不能用现代 Windows runner 通过替代各目标系统实测。

验收报告的 `nativeLegacyVerified` 仅表示当前记录中的真实旧系统已通过对应测试，必须同时保留 OS 版本和测试范围。Win7 SP1（6.1.7601）、Win8（6.2.9200）、Win8.1（6.3.9600）的 native MCP 和完整安装/CEF/更新结果分别记录；任一系统的一次通过不能代表另外两个系统已验证。

## 首版能力边界

| 能力 | 现有 Tauri / WebView2 路径 | 通用 CEF 预览 | Win7/Win8 x64 专版 |
| --- | --- | --- | --- |
| 云端 AIChat 聊天、登录 | 保持现有行为 | 加载 `https://keepwork.com/chat`，独立 profile | 同通用 CEF 预览，仍需逐目标系统实测 |
| 桌面 Bridge v1 | 保持现有行为 | 宠物文字与语音子集，含文档绑定的麦克风采集；不提供文件、终端或通用状态 API | 同通用 CEF 预览 |
| 托管 MCP | 保持现有行为 | Windows 10/11 在加载聊天页前尝试启动内置 Rust MCP；旧系统只使用已有服务，不运行现代 MCP | 启动器在加载聊天页前尝试启动/附着 Win7/Win8 Rust MCP；失败仍打开云聊天 |
| 本地模型 | 保持现有行为 | 不提供 | 不提供 |
| 文件、目录、搜索和普通命令 | 保持现有行为 | 经已连接 MCP 的 HTTP/tool 能力，依服务实际能力提供 | 经已连接 MCP 的 HTTP/tool 能力，保留网页确认和服务安全检查 |

麦克风权限仅允许精确受信任 `/chat` 主页面的主 Frame，经原生提示显式同意；其他来源、子 Frame、登录弹窗、摄像头与屏幕请求继续拒绝。不使用全局 `--enable-media-stream` 免授权，也不把某一页面的许可带给其他来源。权限拒绝、无设备、设备断开或服务错误显示对应失败，不自动重录、重放语音动作或更换目标。

宠物文字消息核对当前主浏览器、主 Frame、精确受信任页面、文档代次、会话上下文及请求 ID；弹窗、子 Frame、其他来源、旧文档、旧会话和重复请求不得改变当前对话。发送前先确认最新草稿已同步；本地草稿仍有未同步编辑时禁止切换目标，须先发送或将编辑恢复为网页当前草稿。面板收起或同一上下文短暂断开不自动覆盖尚未同步的编辑。

恢复主窗口会取消尚未发出的 `input` → `send` 或语音启动后续链，迟到的输入回执不会重新启动发送或录音；已经发出的操作继续按原有请求状态核对，不表示已被取消。现有网页采用先同步输入、再发送的两步协议；原生端和页面适配器会核对已知草稿，但这不是原子的 compare-and-send，不能保证核对草稿与实际发送之间不会发生页面编辑。

请求接受回执不等于模型已回复成功。超时或断开后，发送结果不明时明确提示核对，保留待确认请求和草稿，不自动重新发送、不换请求 ID 重试；账号或会话改变后清理旧投影，旧结果不得进入新上下文。

旧网页未初始化宠物协议、页面未就绪、当前目标不可用或包含附件时，面板给出明确的功能状态，禁止静默丢弃输入或把打开主窗口称为已完成宠物发送。用户仍可打开主窗口处理登录、模型、审批或附件；原有普通聊天和 HTTP MCP 功能继续独立可用。开发时匿名读取 `https://keepwork.com/chat` 指向的 `237372530cfc` 发布模块，已确认已有宠物状态 / 命令 / 回执协议；这只是发布模块的静态核对，未登录、未发送消息，不代表云端生成或 Windows 原生对话已经实测。

本版仍不提供附件编辑、截图授权气泡、网页宠物外观同步、外观尺寸选择或完整动画能力。宠物创建失败时保留主窗口或托盘恢复入口；恢复主窗口、完全退出及异常清理不应留下重复或无法操作的宠物。

Windows 10 1703（15063）及以上 / Windows 11 的「遥控器语音输入…」复用原版 Rust 语音实现，由随包原生进程管理小米 RC001 / RC003 的配对检测、ATVV、云端 ASR 和系统输入，独立于网页与 MCP。按住语音键录音，松手后识别，普通文字输入识别完成时的当前焦点；不自动切回聊天或发送。OK 保持系统原生 Enter，仅发送一次；整句「发送提示词」和「清除提示词」沿用原版精确匹配、修饰键保护与可编辑性检查，停止或退出后的迟到结果不得继续输入。自动开启、手动停止、多个候选设备与权限错误规则见 [小米遥控器语音输入](../README.md#小米遥控器语音输入)。

Windows 7/8/8.1 及 Windows 10 1703 之前的版本不启动该现代 BLE 语音进程，入口说明当前系统不支持，不以电脑麦克风替代遥控器音频。该限制不影响宠物麦克风语音、文字聊天与 HTTP MCP。原版使用的 WinRT `BluetoothLEDevice` 契约要求 Windows 10，所用 `GetGattServicesWithCacheModeAsync` 另要求 1703（15063）及以上；Win32 GATT API 另有 Windows 8 起的接口；本版没有实现或承诺替代的旧系统传输。系统边界依据 [Microsoft BluetoothLEDevice 文档](https://learn.microsoft.com/uwp/api/windows.devices.bluetooth.bluetoothledevice)、[GetGattServicesAsync 文档](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.bluetoothledevice.getgattservicesasync) 和 [Win32 BluetoothGATTGetServices 文档](https://learn.microsoft.com/en-us/windows/win32/api/bluetoothleapis/nf-bluetoothleapis-bluetoothgattgetservices)。

「完全退出」与 `Ctrl+Q` 请求 CEF 正常关闭，等待网页的关闭确认及 CEF 关闭就绪回执后，才销毁主窗口、登录弹窗、托盘和宠物。若网页取消关闭，后续普通关闭仍按隐藏并按偏好显示宠物处理，不遗留待退出状态。隐藏与完全退出均不结束独立 MCP daemon，不接管其他应用拥有的服务。

`0.2.146` 的验证范围为发布网页协议的匿名静态核对、macOS 上的 Windows x64 交叉构建，以及标题栏几何与命中、主题与消息边界、宠物文字协议 / 草稿 / 请求状态和打包检查；Windows 7 SP1、Windows 8、Windows 8.1 的真实文字输入、生成回复、标题栏绘制、托盘与透明宠物显示、点击穿透、拖动、Explorer 重启恢复、安装升级和 CEF 窗口交互仍待分别验收。交叉编译或 fixture 通过不代表云端生成或 Windows 原生交互已验证，报告继续保留 `nativeLegacyVerified: false`。

CEF109 依据实际 Popover API 能力加载无特权兼容脚本，使已发布网页的页面菜单默认隐藏，并支持打开、选择、外部点击关闭及 Escape；原生支持该 API 的内核保持原有行为。该修复由兼容宿主提供，无需同步更新网页或 MCP，不开放文件、终端或其他原生权限。兼容实现针对现有网页菜单，不承诺浏览器完整 top-layer 行为或所有 Popover 规范细节等价；其他 JavaScript / Web API 仍按实际能力处理。

`0.2.148` 为受信任主 `/chat` 页的「全部页面」和「＋」菜单补充限定的布局修复。「全部页面」保留原节点、父节点、页面标签、活动项及事件；打开时临时解除祖先中影响 fixed 定位的滤镜、变换等属性，关闭或节点移除后按原值及优先级恢复，不搬移节点、不更改祖先裁剪或布局。菜单按浏览器视口定位，常规宽 320 CSS px、两侧至少留 8px，默认位于触发按钮下方 6px 并右对齐；空间不足时上翻或限高滚动，窗口缩放及滚动后重新定位。展开箭头朝上、闭合后朝下沿用原版状态提示。保留选页、Escape、外点、重复点击及 iframe 焦点关闭行为，不另抢焦点；「＋」菜单仅修正视口边界，文件 / 工具 / 终端 / 打开浏览器和技能项的内容、顺序及能力灰态保持原协议。

本轮布局独立夹具复用真实 AIChat 会话菜单源码及样式，在 macOS Chrome 156 强制 polyfill 的普通 / 简洁模式下复现旧偏移，并验证修正坐标、窄窗、上翻、节点身份、选择一次执行、焦点与关闭后的样式恢复；它不是真实 CEF109。刷新图标和原生菜单的 Windows GDI 绘制 fixture 仅完成交叉编译，WinPTY 亦完成目标交叉构建；真实 Windows 绘制、DPI、终端交互及三个旧系统验收分别待执行，不据此填写 native 通过或发布完成。

页面标题变化不添加模式后缀；登录弹窗保留常规系统窗口及「Keepwork — 页面标题」，既有 `window.opener` 与登录策略保持不变。主窗口限制为 Keepwork HTTPS 页面；登录弹窗仅允许配置的 Keepwork 登录路径以及 Google、微信、飞书 / Lark、钉钉提供商。常规外链经过策略检查后交给系统浏览器。第三方登录流程还需要实际账号验证，白名单测试通过不代表 OAuth 流程已测试。网页标准文件上传仍可用，从主窗口的 Keepwork 页面发起下载时显示“另存为”对话框；这些浏览器交互不等于开放原生文件 Bridge。

CEF 与 WebView2 使用不同的浏览器数据目录，切换后可能需要重新登录。不要复制两种内核的 cookie 数据库，也不要因切换内核重放待执行操作。原有 Rust 侧配置和工作区授权保持原位置。

与现代桌面端相比，兼容版仍缺少完整文件夹授权 / 文件 / PTY Bridge、页面新建对话与设置命令、宠物动画和外观同步、持久化媒体权限记忆、本地源码服务器、开机启动、托盘登录 / 渠道健康状态，以及完整现代更新窗口等能力。`0.2.146` 补齐文本消息子集，`0.2.153` 增加上述语音与输入能力；它们不表示全部桌面 Bridge 已移植。后续建议先为可选页面命令补充就绪与能力握手，再接入「新建对话 / 设置」：旧网页不支持时隐藏相应操作，不要求更新 MCP，不把无响应视为执行成功。该建议属于后续切片，不是本版已提供能力。

## 内核选择与系统边界

以下自动选择规则适用于通用兼容预览；Win7/Win8 专版固定使用 legacy CEF109，不探测或启动现代 Tauri。

- Windows 10 及更高版本：WebView2 可用时启动现有 Rust / Tauri 客户端；不可用时选择现代 CEF 宿主包。
- Windows 7 SP1 / 8 / 8.1：选择 legacy CEF 宿主，不尝试先启动现代 Rust 程序；不支持未安装 SP1 的 Windows 7。
- 普通网页加载失败、登录失败或网络中断，不应被当作 WebView2 缺失。
- 当前阶段仅能声明经过构建和实测的体系结构，不能因为 CEF 上游存在某架构就承诺其安装包可用。

CEF 宿主使用同一 Windows 会话内的固定单实例锁，覆盖所有 CEF 通道和 profile。启动器在探测 WebView2 之前检查已有 CEF 实例；隐藏到托盘的宿主仍占用此锁，可从托盘恢复已有窗口。切换内核或更新前须先选择「完全退出」，避免跨内核重复启动。

通用兼容安装包构建脚本只提供 **x64 和 ARM64**；独立 Win7/Win8 专版仅提供 **x64**。虽然宿主协议和 CEF109 源码支持 x86 构建，本次没有提供 32 位 Windows 的兼容安装包。

现代 CEF 包默认最低系统为 Windows 10 build 19045；发布者可根据具体 SDK 的实际测试结果设置更高或更低的 `minWindows`。启动器会执行这个下限，不能把“Windows 10”整体视为已测试平台。

Windows 7 使用 **CEF 109**，它是最后兼容该系统的官方分支，已经停止维护。现代 Windows 使用另外构建、验证和锁定版本的现代 CEF 包；“最新版”不等于给 Windows 7 下载现代 CEF。新旧 CEF 的宿主和 DLL 不能混用。相关系统边界见 [CEF 官方分支支持表](https://github.com/chromiumembedded/cef/blob/master/docs/branches_and_building.md)和 [Windows 7 / 8 支持结束公告](https://groups.google.com/g/cef-announce/c/Lpw5PP5LPNc)。

独立宿主按照 CEF 的 Windows 沙箱架构构建：CEF 109 将 `cef_sandbox.lib` 链接进宿主 EXE；现代 CEF 使用 SDK 提供的 `bootstrap.exe` 和宿主 DLL，并将沙箱上下文传给 CEF 初始化与子进程入口。不可通过 `--no-sandbox` 解决打包或启动问题。现代 CEF M138 起的这一构建要求见 [CEF 官方沙箱说明](https://github.com/chromiumembedded/cef/blob/master/docs/sandbox_setup.md)。这与把当前应用升级到 Tauri 3 alpha 是不同的实现路径。

Win7/Win8 构建还必须锁定旧系统可用的 `D3DCompiler_47.dll`：本轮实际 CEF109 SDK 所附 DLL 来自更新的系统版本，不能只因 CEF 主版本为 109 就接受所有附带依赖。legacy payload 通过 `prepare-win7-cef.py` 从微软官方 Windows 8.1 SDK redist 准备匹配 DLL，校验固定 CAB 与 DLL 的 SHA-256 后替换，来源与摘要锁随构建证据保留。DirectX 官方作者的[平台支持与 app-local 分发说明](https://walbourn.github.io/hlsl-fxc-and-d3dcompile/)说明该 SDK 的编译器 DLL 支持 Win7/Win8.x，并可随 Win32 桌面程序在应用目录分发；不从构建机系统目录或任意 DLL 下载站取替代文件。

该精确微软 redist 的原始 PE `OSVersion` 为 6.3、subsystem 版本为 6.0。静态审计只对来源锁中固定 SHA-256 对应的这个文件允许该 `OSVersion` 元数据例外，不修改 DLL 的 PE 头，也不按文件名、所有微软 DLL 或所有 legacy 依赖泛化放宽。架构、原有 subsystem 阈值、导入 API、清单签名和归档校验继续执行。此例外依据特定厂商兼容声明及可重复来源，不表示 CEF/GPU 已在三个旧系统运行通过；三系统的未实测状态必须保留，发布实测豁免按 rust-release Skill 记录。

外层启动器必须自身兼容 Windows 7。当前应用使用的 Tauri 2.12 已停止官方 Windows 7 支持，单纯在它的 `main` 中增加 OS 判断不能消除 Windows 加载器的失败。详见 [Tauri 2.12 公告](https://v2.tauri.app/blog/tauri-2.12/)。仓库原有 Electron 下载启动器使用 Go 1.25，也不能直接作为 Windows 7 入口；[Go 1.21 起要求 Windows 10](https://go.dev/doc/go1.21)。

Win7/Win8 专版的 C++ 构建固定使用 VS 2022 v143 / MSVC 14.44、Windows SDK 10.0.22621.0；CI 使用 `windows-2022`，不随 `windows-latest` 升级到 VS 2026。微软在 [MSVC 14.50 的 STL 变更](https://github.com/microsoft/STL/releases/tag/msvc-build-tools-14.50)中移除了 Win7/Win8/Win8.1 目标支持，并让 `filesystem` 直接调用 Win8 API。仅设置 `_WIN32_WINNT` 不能改变预编译标准库的导入，因此专版配置会拒绝 MSVC 14.50+，并继续对真实 Launcher 和完整 payload 执行既有 PE 审计。现代版工具链保持各自流程。

## 下载、缓存与发布契约

CEF 分发包需要包含匹配版本的宿主 EXE、CEF 二进制、子进程所需文件、locale 和其他资源，不能只上传 `libcef.dll`。构建时确定 CEF 版本，应用启动时选择经过发布验证的包，不从上游任意获取 DLL 替换。

发布清单通过 RSA-2048 / SHA-256（PKCS#1 v1.5）签名，启动器使用内置公钥和 Windows BCrypt 验签，再检查包的下载大小和 SHA-256。私钥只用于发布签名，不进入源码、安装包或下载缓存。操作系统代码签名与清单签名是不同环节，不能相互替代。

Win7/Win8 正式发行使用仓库固定的 [`keys/win7-release-public.pem`](../keys/win7-release-public.pem)，其 SPKI DER SHA-256 指纹为 `f13040d39f44db78c37d5457d0e05c2d845b591d9e16f95f20999addecd62f4a`。GitHub secret `WIN7_RELEASE_PRIVATE_KEY_PEM` 保存对应私钥；production 构建必须先核对该私钥导出的公钥与固定公钥一致，不匹配时停止，不能回退预览密钥。发布器的 `--public-key` 指向此仓库公钥。私钥的本机备份保存在仓库外的受限目录，不进入 artifacts；后续构建复用同一密钥，缺失时先恢复备份，不自动重新生成。已安装启动器固定此信任根，更换密钥需要单独的客户端迁移方案。预览构建继续使用临时密钥，其产物不能提升正式 feed。

包先下载并解压到暂存目录。解包必须限制条目数量和总大小，拒绝绝对路径、路径穿越以及可写出暂存目录的成员。宿主完成本地空白页渲染并发出原生就绪信号后，才将候选缓存置为当前版本；中断下载、校验失败、解包失败或启动失败不能覆盖已验证的可用缓存。

新的 CEF CDN 命名空间需要单独发布，不应覆盖现有桌面更新和 MCP feed。仓库代码或测试 fixture 中存在 URL 并不代表该 URL 已有可下载产物。首次发布必须先构建实际 Windows 包、配置匹配的签名公钥，并完成验收或记录用户授权的实测豁免，再发布清单与包。

启动器约定的 CDN 根路径是 `https://cdn.keepwork.com/keepwork/aichat-cef/v1/`：

- 清单：`<legacy|modern>/windows-<x86|x64|arm64>/stable.json`，legacy 不接受 ARM64。
- 宿主包：`objects/<sha256>.zip`，包地址由校验后的摘要推导，不接受清单指定的任意下载 URL。
- 兼容安装的现代 Rust 客户端更新清单：`client/windows-<arch>/latest-client.json`，与常规 Tauri 安装包 feed 隔离，更新时保留外层兼容启动器。显式 `AICHAT_UPDATE_FEED_URL` 仍优先于默认路径。
- 本机缓存：`%LOCALAPPDATA%\Keepwork\BrowserRuntimes\<channel>\<arch>`，其中 `active.json` 保存已验证的清单，`versions\<sha256>` 保存对应文件。
- CEF profile：`%LOCALAPPDATA%\Keepwork\CefProfiles\<channel>-<chromiumMajor>`。大版本升级使用不同目录，可能需要再次登录。

兼容启动器的常用参数：

```powershell
# 自动检测系统和 WebView2
.\Keepwork.exe

# 强制进入当前系统对应的 CEF 通道，使用已验证缓存
.\Keepwork.exe --cef

# 重新读取该通道的发布清单，下载并验证候选版本
.\Keepwork.exe --update-cef
```

默认使用可用缓存，不在每次启动时联网更新 CEF；专版客户端升级带来的更高版本内置宿主按前述规则尝试激活。使用 `--update-cef` 主动检查 CDN。更新失败会保留原来的 `active.json`，再次正常启动可使用旧缓存。发布新内核不会让已经运行的进程自动切换。`--background` 可以与以上参数组合；从 `0.2.142` 起，CEF 宿主在托盘注册成功后隐藏主窗口，可从托盘恢复；`0.2.143` 开启桌面宠物时还会显示宠物。托盘注册失败时仍显示窗口。

这里的 CEF 内核失败处理是保留旧版本，不是自动重新启动旧版本：首版不会在内核启动失败后读取 `previous.json` 并自动切换。它不同于 Win7/Win8 MCP 候选失败后的已验证 active 尝试。中断下载也没有断点续传，重试从头下载；若进程异常退出留下暂存目录，启动器会报错要求在关闭 Keepwork 后移除该暂存目录，再重试。不要删除 `CefProfiles` 中的浏览器数据。

WebView2 检测会实际创建控制器。启动现代 Rust 程序时，启动器还通过 `--webview-ready-event` 等待主窗口就绪；只有主 WebView 创建失败对应的明确退出码 `86` 才触发后续 CEF 回退。普通崩溃、等待超时或网页错误均不触发自动切换，避免掩盖其他启动问题。

## CEF 宿主构建与策略测试

以下命令从 `apps/aichat-rust` 目录执行。宿主需要匹配目标架构的 Windows CEF binary distribution。构建用下载器从 CEF Automated Builds 的 HTTPS 索引选择匹配通道的最新稳定 standard SDK：legacy 只选 109，modern 只选 138 及以上。下载时验证索引中的大小与 SHA-1，并额外记录 SHA-256 供重复构建锁定；这是构建工具，最终用户仍从 Keepwork CDN 下载已经构建、验签的宿主包。

使用 Python 3.12 或更新版本。下载器会在网络请求和创建输出目录之前检查 `tarfile` 的安全 `data` 过滤能力；缺失时报告实际解释器路径与版本，不降级为无过滤解压。Node 测试默认使用 Windows 的 `python` 或其他平台的 `python3`；安装了多个 Python 时，可先设置 `PYTHON` 为受支持解释器的完整路径再运行测试。直接执行下载器时，应直接使用该解释器运行下列脚本。

```powershell
# Python 3.12；每次使用新的输出目录
python scripts/fetch-cef-sdk.py --channel legacy --arch x64 --output build/sdk-legacy
python scripts/fetch-cef-sdk.py --channel modern --arch x64 --output build/sdk-modern

# 重复构建时复用记录的版本和 SHA-256，不重新选择最新版
python scripts/fetch-cef-sdk.py --channel modern --arch x64 --output build/sdk-modern-repeat --lock build/sdk-modern/cef-sdk-lock.json
```

输出目录中的 `cef-root.txt` 给出 SDK 的绝对路径，`cef-sdk-lock.json` 记录所选版本、架构和摘要。将 `CEF_ROOT` 指向该路径。CEF 109 必须包含 `Release/cef_sandbox.lib`，现代 SDK 必须包含 `Release/bootstrap.exe`。不要用不带沙箱资源的 SDK 绕过构建检查。

```powershell
# Windows + MSVC，x64 示例；Win32 / ARM64 应选择对应架构和 SDK
cmake -S windows/cef-host -B build/cef-legacy -A x64 -DCEF_ROOT=C:/sdk/cef109
cmake --build build/cef-legacy --config Release

# 使用另一个构建目录生成现代宿主
cmake -S windows/cef-host -B build/cef-modern -A x64 -DCEF_ROOT=C:/sdk/cef-modern
cmake --build build/cef-modern --config Release
```

输出位于各构建目录的 `payload/Release/`，其中 `cef-host.json` 记录版本、架构与沙箱模式。这个目录用于后续签名和生成 CEF 分发归档，不直接复制到 Tauri `resources` 或历史通用兼容安装包。Win7/Win8 完整包通过 `--cef` 接受校验后的已签名归档；不人工拼装或复制 DLL。现代宿主为官方 bootstrap EXE 加 `keepwork-cef.dll`，legacy 宿主为链接沙箱库的 EXE。

宿主入口为 `keepwork-cef.exe --profile <绝对路径> --ready-event <原生命名事件>`，通常由兼容启动器调用。`--background` 使主窗口初始最小化。就绪信号在主框架完成初始 `about:blank` 加载后发送，随后才导航到聊天页；它覆盖本地渲染器与沙箱启动，不依赖远端网站请求成功，因此断网不会被误判成内核启动失败。若同一 Windows 会话已有 CEF 实例，宿主返回退出码 `17`；不能把旧实例的运行状态当作候选包就绪。

导航策略测试不需要 Windows 或 CEF SDK，可在开发机运行：

```sh
cmake -S windows/cef-host -B build/cef-policy -DKEEPWORK_POLICY_TESTS_ONLY=ON
cmake --build build/cef-policy
ctest --test-dir build/cef-policy --output-on-failure
```

## 兼容安装包与 CDN 文件准备

下列现代桌面 payload 和 `build-windows-compat.cjs` 步骤属于通用兼容预览。Win7/Win8 专版不使用此 payload；其独立构建与打包入口见前述专版契约及 Skill 参考流程。CEF 宿主本身的构建、签名和缓存规则继续共用。

发布方需要一对持久使用的 RSA-2048 PEM 密钥。示例中的 `C:/release-keys/cef-public.pem` 与 `cef-private.pem` 是发布方准备的路径，不是仓库提供的密钥。不要提交私钥；若更换公钥，需要重新分发固定该公钥的启动器。

CEF 宿主的所有二进制修改和代码签名都应在生成分发清单之前完成。打包脚本读取宿主构建生成的 `cef-host.json`、检查 PE 架构和资源文件、生成 ZIP 与签名清单：

```powershell
# 生成 legacy CEF109 包；默认最低系统为 Windows 7 SP1
node scripts/cef-release.cjs package build/cef-legacy/payload/Release build/cef-release C:/release-keys/cef-private.pem

# 生成现代 CEF 包，最后的最低系统参数可选
node scripts/cef-release.cjs package build/cef-modern/payload/Release build/cef-release C:/release-keys/cef-private.pem 10.0.19045

# 若单独编译原生启动器，可先生成只含公钥的 C++ 头文件
node scripts/cef-release.cjs key-header C:/release-keys/cef-public.pem build/cef-release-key.hpp
```

输出包括 `objects/<sha256>.zip`、通道清单和 `release-plan-<channel>-<arch>.json`。它们是待审查、待上传文件；脚本不会上传 CDN。发布时先上传不可变 ZIP 对象，确认下载与摘要，再发布相应通道的 `stable.json`。不能改写已发布 SHA-256 路径下的内容。

发布工具默认仅校验签名、大小和摘要并输出计划，不写 CDN：

```powershell
node scripts/publish-cef.cjs build/cef-release legacy x64 C:/release-keys/cef-public.pem
node scripts/publish-cef.cjs build/cef-release modern x64 C:/release-keys/cef-public.pem
```

发布负责人在完成 Windows 验收并核对计划后，才可显式添加 `--publish`。真正发布使用 `KP_QINIU_ACCESS_KEY` / `KP_QINIU_SECRET_KEY`，先上传和验证宿主 ZIP，再更新通道清单。本次没有执行发布。此工具只处理 CEF 宿主通道，不发布兼容安装包的客户端更新 feed。

兼容安装包使用已准备的现代桌面 payload，再编译并加入原生启动器。payload 应包含对应架构的 `aichat-rust.exe` 及其所需资源；这个脚本不替代 Tauri / MCP 构建：

```powershell
node scripts/build-windows-compat.cjs --payload C:/build/modern-desktop-payload --output C:/build/compatible-installer --key C:/release-keys/cef-public.pem --arch x64
```

该步骤需要 Windows、MSVC / Windows SDK、CMake 和 NSIS。CEF 宿主包与兼容安装包是两个独立产物：不要把前面的 `payload/Release` 目录作为这里的现代桌面 payload，也不要将 CEF DLL 放进安装包。开发或发布机器使用 Node / Python 不意味着最终用户需要安装它们。

构建输出为 `Keepwork-Compatible_<version>_<arch>-setup.exe` 和描述其大小 / 摘要的 `compatible-installer.json`。每次使用新的输出目录；现存安装 staging 目录会使构建停止。安装目标为当前用户的 `%LOCALAPPDATA%\Programs\KeepworkCompatible`，桌面快捷方式和开始菜单入口均为「Keepwork 兼容版」，指向安装目录中的 `Keepwork.exe`，与常规桌面安装路径分开。卸载清理对应快捷方式，保留浏览器 profile 和已验证下载缓存。

安装包描述包含预定下载地址 `https://cdn.keepwork.com/keepwork/aichat-cef/v1/client/windows-<arch>/<installer>`；它和同目录的 `latest-client.json` 仍需另行发布。生成描述中的 URL 不代表安装包或更新清单已存在，不能将其当作已上线链接。

兼容打包脚本不自动执行 Authenticode 代码签名。正式发布需为启动器、宿主和最终安装包安排对应的签名 / 验签步骤；签名改变文件内容后，必须重新生成受影响的包摘要、签名清单或安装包描述，不能继续发布旧摘要。

## 历史通用兼容预览工作流

[`.github/workflows/aichat-rust-cef.yml`](../../../.github/workflows/aichat-rust-cef.yml) 提供手动触发的 x64 预览构建：构建现有 Rust 客户端和 MCP、生成不含 CEF 的 NSIS 安装包、下载并分别构建最新匹配的 legacy / modern SDK，以及执行原生校验工具和策略测试。产物分别携带安装包、CEF 宿主包、SDK 锁文件和预览公钥。

该工作流每次生成独立临时 RSA 密钥，私钥不上传 artifact 并在任务结束时删除；它不是正式发布的信任根。预览安装包与包清单只适合隔离验证，不能直接替换正式通道，工作流也不写 CDN。它不是 Win7/Win8 专版工作流；即使构建通过，也不能替代 Win7/Win8/Win8.1 虚拟机中的安装、渲染、登录和下载验证。
