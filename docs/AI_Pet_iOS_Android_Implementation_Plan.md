# AI 桌面宠物：iOS 与 Android 双端实现方案

版本：1.0｜日期：2026-11-12｜用途：产品定义、技术设计与开发 Agent 执行

## 1. 目标与路线

打造同一个具有角色、记忆、文字和语音交互能力的 AI 宠物，在两种移动系统上采用不同展示方式：

- **Android：跨应用悬浮宠物。** 用户主动开启后，在桌面和允许悬浮覆盖的其他 App 上显示透明角色；点击打开聊天面板，支持文字输入和主动发起语音会话。
- **iOS：App 内完整宠物＋桌面小组件＋有限时长的实时活动。** App 内提供完整互动；离开 App 后通过小组件和支持设备上的灵动岛/锁屏实时活动体现陪伴状态，点击回到聊天。画中画仅列为独立研究项，不作为 MVP 依赖。
- **共享服务：** 身份、角色配置、对话、记忆、语音和资产分发保持一致；显示层和生命周期按平台原生实现。

本方案是开发设计，不是已完成的可运行产品或商店审核承诺。涉及性能、周期的数据均为工程目标，需真机验证。

## 2. 能力边界

| 能力 | Android | iOS |
|---|---|---|
| App 内透明角色、动画、点击互动 | 支持 | 支持 |
| 跨其他 App 显示自由悬浮宠物 | 经悬浮窗授权可实现 | 普通第三方 App 无通用公开接口 |
| 悬浮角色拖动、贴边、气泡 | 支持，受窗口规则约束 | 不作为跨应用能力提供 |
| 文字输入 | App 内或可获取焦点的悬浮面板 | App 内；小组件提供快捷动作/跳转 |
| 语音输入输出 | 权限及服务条件满足后支持 | App 内支持；后台语音独立处理 |
| 桌面入口 | 可选小组件 | WidgetKit 小组件 |
| 限时陪伴状态 | 通知或 App 状态 | ActivityKit 实时活动 |
| 永久不被系统终止 | 不保证 | 不保证 |
| 自动读取其他 App 内容 | 悬浮窗本身不赋予此权限 | 不提供 |

Android 悬浮层高于普通 Activity，但低于部分关键系统窗口；其他 App 可隐藏覆盖层。[1][2] iOS 小组件和实时活动不是持续运行的游戏画布，也不支持在其中嵌入完整聊天编辑器。[5][6]

## 3. MVP 产品范围

### 必须交付

1. 一只基础宠物，具备 idle、happy、listening、thinking、speaking、sleeping、error 七种状态。
2. 双端 App 内聊天：文字、点击录音、语音回复、停止播放、取消生成。
3. Android 悬浮宠物：开启/关闭、拖动贴边、点击展开、文字气泡、退出入口。
4. iOS 小组件：宠物形象、简短状态、打开聊天；支持版本上提供一个简单互动动作。
5. iOS 实时活动：用户启动明确时长的陪伴/专注会话，显示剩余时间和宠物状态，能够结束。
6. 最近对话持久化；可选长期记忆、查看和删除记忆。
7. 权限拒绝、断网、后台中止、账号退出的明确降级。

### 后续迭代

多宠物、皮肤、跨设备同步优化、连续语音、精细口型、有限主动提醒、可选 Android 小组件、真实场景下的 iOS PiP 验证。

MVP 不承诺全天候唤醒词监听、自动操作其他 App、自动读取屏幕、锁屏上任意悬浮或 iOS 全局透明桌宠。

## 4. 技术架构与工程组织

默认采用 **Android Kotlin 原生＋iOS Swift/SwiftUI 原生＋共享后端协议**。原因是核心差异集中在窗口、音频、服务和系统扩展；先确保平台能力可靠，再考虑共享更多业务代码。

如果已有 Flutter/React Native 项目，保留已有 App 界面；Android 悬浮层、服务、iOS Widget Extension 和 ActivityKit 仍通过原生模块实现。不要为统一技术栈重写成熟工程，也不要把 H5 当成获取全局悬浮权限的方式。

| 模块 | 责任 |
|---|---|
| PetRenderer | 角色资产、动画切换、口型、低功耗模式 |
| PetStateStore | 宠物状态、设置、陪伴会话、持久化 |
| ChatCoordinator | 消息队列、流式响应、取消与重试 |
| VoiceSession | 录音、端点检测、播放、音频中断 |
| AndroidOverlayHost | 悬浮窗、输入焦点、拖动、系统栏适配 |
| IOSCompanionSurfaces | 小组件、实时活动、深链与系统动作 |
| BackendGateway | 鉴权、对话、ASR/TTS、限流、记忆 |

建议目录：`apps/android`、`apps/ios`、`services/api`、`packages/contracts`、`assets/pets`、`docs`。共享 JSON Schema、角色配置、资产及服务契约；不要把 SwiftUI 视图或 Android View 视为可直接共享代码。

初始版本建议 Android 8/API 26 起、iOS 17 起，以缩小 MVP 适配范围；这是产品建议而非全部 API 的最低版本。发布时使用商店要求的当前 target/SDK，并按实际设备覆盖需求调整。

## 5. Android 实现

### 5.1 悬浮窗与输入

- 使用 `WindowManager` 和 `TYPE_APPLICATION_OVERLAY`，开启前检查 `Settings.canDrawOverlays()`。
- 用户点击“开启桌面宠物”后解释用途，再通过 `ACTION_MANAGE_OVERLAY_PERMISSION` 引导授权；返回 App 后重新检查结果。
- 主宠物使用尽可能小的透明窗口，默认不可获取键盘焦点；不要用全屏透明窗口包住角色。
- 点击展开独立聊天面板；需要文字输入时调整焦点标志并调用输入法，收起后释放焦点、隐藏键盘。
- 角色拖动与点击使用移动阈值区分；限制在可见安全区域内，处理旋转、刘海、系统栏、键盘和折叠屏尺寸变化。
- 透明像素不等于自动触摸穿透。按窗口边界、触摸区域及 Android 不可信覆盖层规则处理，不拦截角色范围之外的底层交互。[1]
- 若某设备悬浮输入体验不可靠，点击“文字聊天”打开正常 Activity；不要让输入错误阻断整个宠物功能。

### 5.2 服务与权限

悬浮显示和麦克风会话分开管理，权限按需请求：

| 权限/声明 | 用途 | 时机 |
|---|---|---|
| `SYSTEM_ALERT_WINDOW` | 跨应用悬浮 | 用户开启桌宠 |
| `FOREGROUND_SERVICE` | 合法前台服务 | 按服务设计声明 |
| 对应 FGS 类型权限 | 适配具体服务用途 | 按目标系统声明 |
| `RECORD_AUDIO` | 语音输入 | 用户首次点击语音 |
| `POST_NOTIFICATIONS` | 支持版本上的通知授权 | 解释陪伴通知后请求 |

长期可见宠物服务如无更准确的服务类型，可评估 `specialUse`；Android 14+ 对应 `FOREGROUND_SERVICE_SPECIAL_USE`，并填写 `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 说明真实用途。它需要商店审查，**不是通用保活豁免，也不保证批准**。[3]

不要为了运行宠物谎报 `mediaPlayback`、`location` 或 `dataSync`。前台服务必须正确调用 `startForeground()` 并提供通知；通知权限被拒绝也不能省略服务通知要求。通知提供“打开聊天”“暂停/停止宠物”等操作。

### 5.3 语音流程

最稳妥的首版流程：悬浮宠物点击语音 → 打开可见的语音 Activity → 检查麦克风授权 → 启动录音；若需要在切换 App 后继续会话，再在允许的前台状态下启动正确类型的 microphone FGS。

持续录音服务需声明 `microphone` 类型及相应权限。存在悬浮窗并不自动满足麦克风 while-in-use 权限和服务启动条件；Android 15+ 关于可见覆盖层的规则也不是麦克风授权替代品。[4]

用户停止、超时、权限撤回或音频中断后释放录音资源。首版不依赖后台任意时刻自动开麦。

### 5.4 生命周期

- 用户停止服务后真正移除窗口并停止任务，不自动重启。
- 进程重建只恢复配置和合法状态，不擅自恢复录音。
- 屏幕关闭时停止宠物逐帧绘制；解锁后重新判断是否显示。
- 退出账号、权限撤销时移除窗口，取消网络请求并清理敏感状态。
- 针对各厂商省电策略真机记录行为；按需解释系统设置，不承诺常驻成功率。

## 6. iOS 实现

### 6.1 App 内宠物

SwiftUI 实现聊天及设置；角色渲染可采用轻量帧动画或 SpriteKit。录音/播放通过 AVFoundation 的音频会话与音频引擎管理，ASR/TTS 经服务适配层调用。

MVP 默认前台录音：进入后台时结束录音并提示状态。若产品确需后台持续语音，作为独立能力实现合适的 audio 后台模式与音频会话，真机验证切后台、锁屏、来电和蓝牙切换；不以播放无声音频等方式保持普通宠物逻辑运行。[8]

### 6.2 小组件

- 建立 Widget Extension，使用 WidgetKit/SwiftUI。
- 通过 App Group 共享精简的宠物状态快照，不把全部聊天记录放进组件数据。
- 展示角色图、状态和上次更新时间；敏感内容默认隐藏。
- 使用深链定位至对应宠物聊天；简单动作通过支持版本上的 App Intents 实现。
- 由 App 更新共享快照并请求时间线刷新，不能假设请求立即执行。
- 离线时显示最后已知状态；不在组件里维持 WebSocket、麦克风或动画循环。[5]

### 6.3 实时活动与灵动岛

将其定义为用户明确启动的“25/50 分钟陪伴专注会话”或其他真实限时活动，而不是假装无限存活的宠物服务。

1. 检查实时活动可用性和授权状态。
2. 创建 `ActivityAttributes`：静态字段为 `petId`、`sessionId`；动态字段包含开始/结束时间、状态与简短标签。
3. 提供锁屏布局及灵动岛 compact/minimal/expanded 布局；没有灵动岛的设备仍可使用支持的锁屏展示。
4. 倒计时使用系统时间展示能力，不让后台进程每秒更新。
5. 用 App 内 ActivityKit 或适当的 ActivityKit push 更新；状态变化才更新，不以推送驱动角色逐帧动画。
6. 活动结束或用户停止时调用结束逻辑，并同步后端会话。

当前文档描述实时活动最多活跃 8 小时，之后可能在锁屏额外保留最多 4 小时；实现时再次核对目标 OS 文档。实时活动不能自行联网，静态与动态数据合计有 4 KB 限制，因此只存精简状态、使用本地资产。[6]

### 6.4 PiP 可选验证

不纳入首版承诺。如果未来存在符合用途的视频播放或视频通话场景，可独立验证 `AVPictureInPictureController`。视频通话 PiP 不接收自定义视图触摸事件，无法在其中放可点击的聊天输入框。[7]

AI 角色画面能否构成适当 PiP 用途，需要结合真实产品功能和审核反馈验证，不能仅凭技术上渲染成功推定可上架。普通视频/通话 PiP 也不能变成系统全局透明异形宠物。实验失败时保留 App＋小组件＋实时活动路线。

## 7. 角色、对话与语音协议

角色资产首版采用原创或具有明确商用许可的 2D 图集；每个动画配置帧、时长、循环方式及锚点。禁止仅凭开源代码许可推断角色形象和音色可商用。

状态流：`idle → listening → thinking → speaking → idle`；错误进入 `error` 并提供重试，用户停止回到 `idle`。外观状态由本地事件驱动，模型只提供允许范围内的情绪提示，不直接控制系统权限或执行任意指令。

建议统一消息模型：

```json
{
  "schemaVersion": 1,
  "conversationId": "conv_example",
  "messageId": "msg_example",
  "clientRequestId": "request_example",
  "petId": "pet_default",
  "role": "user",
  "inputMode": "text",
  "text": "陪我练习五分钟日语",
  "locale": "zh-CN"
}
```

服务端流事件统一为：`text.delta`、`text.done`、`emotion`、`audio.chunk`、`audio.done`、`error`、`done`。事件包含 `requestId`、序号和必要的音频格式信息；重连按请求标识去重，过期响应不得继续播放。

| 接口建议 | 用途 |
|---|---|
| `POST /v1/conversations` | 创建会话 |
| `POST /v1/conversations/{id}/messages` | 提交消息并获取流式结果 |
| `POST /v1/voice/sessions` | 创建短期语音会话 |
| `POST /v1/requests/{id}/cancel` | 取消生成/语音 |
| `GET/PATCH /v1/pets/{id}/state` | 角色与设置同步 |
| `GET/DELETE /v1/memories/{id}` | 查看或删除记忆 |
| `POST /v1/companion-sessions` | 创建限时陪伴活动 |

API 是待实现契约，不代表现成供应商接口。首版采用“录音→ASR→LLM→TTS”串联，先验证完整链路；第二阶段再实现实时双向语音和打断。音频编码、采样率与传输协议由供应商能力协商，不能假定所有接口都支持相同格式。

TTS 播放开始/结束驱动 speaking 状态；初版用振幅驱动简单口型即可。无网络时保留本地动作并显示不可联网，不伪造 AI 回答。长期记忆默认可选，只保存用户确认的信息；云端 API 密钥不打包到客户端。

## 8. 性能与体验目标

以下为首轮测试目标，不是平台保证：

| 项目 | 初始目标/策略 |
|---|---|
| 点击至本地视觉反馈 | 100 ms 内 |
| 宠物动画 | 活跃 24–30 FPS，闲置降帧或静止 |
| 模型首段文字 | 良好网络下 p50 ≤2 s，记录 p95 |
| 语音结束至首段播放 | 串联方案 p50 ≤3 s，超时有反馈 |
| 资产下载 | 首包仅内置基础角色，其他按需缓存 |
| 闲置网络 | 不轮询生成，不持续上传音频 |
| 熄屏/不可见 | 停止无意义绘制，保留必要会话处理 |

不能先给出统一电池消耗承诺。以同设备、同亮度、同网络的“未开启宠物”作对照，分别测试静置悬浮、频繁动画、文字聊天、连续语音 30/60 分钟，记录电量、CPU、内存、温度及后台中止情况。

## 9. 实施顺序与交付门槛

周期假设：已有模型服务接入经验，Android/iOS 各有开发能力，并有后端与测试支持。以下约 4–6 周为排期估计，商店审核和厂商适配可能延长。

| 阶段 | 工作 | 完成条件 |
|---|---|---|
| 0：能力验证，2–3 天 | Android 悬浮＋键盘＋FGS；iOS 小组件＋实时活动 | 真机录像和限制记录，确认平台路线 |
| 1：基础链路，约 1 周 | 双端 App、角色状态机、文字后端 | 两端完整文字问答，取消与断网有效 |
| 2：系统入口，约 1 周 | Android 生命周期；iOS 扩展与深链 | 入口、退出、权限拒绝和恢复可验证 |
| 3：语音与记忆，约 1 周 | ASR/TTS、音频中断、记忆管理 | 录音/播放正确释放，可删除数据 |
| 4：稳定性，1–2 周 | 厂商适配、功耗、商店材料 | 关键测试通过，阻塞项清零 |

优先完成阶段 0，再投入精细角色动画。平台限制验证失败时明确降级，不能用假界面掩盖能力缺失。

## 10. 验收清单

### Android

- [ ] 拒绝悬浮窗权限仍能使用 App 内聊天。
- [ ] 主屏和至少两类普通 App 上可显示、拖动、贴边；宠物外区域可正常操作。
- [ ] 展开聊天后键盘输入正常；收起后键盘与焦点均释放。
- [ ] 受保护页面隐藏覆盖层时不尝试绕过，不导致服务崩溃。
- [ ] Android 14+ 麦克风服务启动符合条件，无后台开麦异常。
- [ ] 通知、设置及宠物菜单均有明确退出方式。
- [ ] 撤权、旋转、熄屏、进程终止、用户强制停止均有记录和正确行为。
- [ ] 至少验证一个接近原生系统设备和两个目标市场厂商设备。

### iOS

- [ ] App 内文字、语音、表情完整可用。
- [ ] 小组件显示缓存状态并准确跳转到对应宠物。
- [ ] 实时活动仅对应用户启动的真实限时会话，结束后状态一致。
- [ ] 分别验证有/无灵动岛设备及关闭实时活动的情况。
- [ ] App 挂起后组件/活动能合理显示最后状态，不假定 JS/Swift 逻辑持续执行。
- [ ] 前台录音方案切后台会结束录音；如另做后台语音，必须单独验证。
- [ ] 未采用无声播放、伪 VoIP 或非预期后台模式保持桌宠运行。

### 通用

- [ ] 网络超时、模型失败、音频中断、切换输出设备、取消和重复提交均可恢复。
- [ ] 模型密钥仅在服务端，日志不默认记录原始音频或敏感对话。
- [ ] 支持删除对话和长期记忆，并定义服务端删除范围与保留期限。
- [ ] 交付可安装构建、构建步骤、服务配置示例、已知限制、测试设备与结果。

## 11. 可直接交给开发 Agent 的执行要求

请将本文作为产品与技术规格，实现 Android 悬浮宠物和 iOS App＋小组件＋实时活动双端 MVP。

先审查现有仓库结构和版本，不覆盖已有功能或无关修改。列出可复用模块及平台缺口，然后按阶段 0 到 4 实施。优先使用已有技术栈，系统窗口和扩展能力采用原生实现。每个阶段交付可验证结果与已知限制。

必须做到：

1. 先跑通真实设备的系统能力，再做角色美化。
2. Android 不把悬浮权限当成麦克风或永久后台运行许可；验证服务类型和商店申报。
3. iOS 不承诺跨应用透明桌宠，不把小组件或实时活动当成常驻渲染容器。
4. 小组件与实时活动只呈现精简状态；真实输入在 App 内完成，简单按钮按系统能力实现。
5. 语音会话必须有明确开始、结束、取消及音频中断处理。
6. 共享服务协议、资产和角色状态定义；平台生命周期分别实现。
7. 缺少模型凭据时使用明确标注的开发 Mock，并保留生产适配层；不能宣称 Mock 已接通真实服务。
8. 完成必要的状态机、取消/去重与数据隔离测试，并进行系统功能真机验收；不能用单元测试代替权限和后台验证。
9. 明确区分已编码、已构建、已真机验证和待商店审核四种状态。
