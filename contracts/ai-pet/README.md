# AI Pet candidate contracts — 0.1.0-dev.4

**Unpublished, offline development package. Pending canonical service agreement.** These schemas and deterministic checks implement a first M0 slice of the accepted AI Pet specification. They are not live APIs, a cloud identity provider, a historical exporter, an atomic billing ledger, or evidence of device behavior. No endpoints, real accounts, microphone consumers or network consumers are present. The package is private and independently versioned; existing products are unchanged.

## Reproduce

From the repository root with Node.js 22 or later and npm:

```sh
npm ci --prefix contracts/ai-pet --ignore-scripts --no-audit --no-fund
npm test --prefix contracts/ai-pet
```

Only the first dependency install needs registry access. Dependencies are pinned in the app-local lockfile. Tests use Node's built-in test runner and Ajv's Draft 2020-12 validator; no build step or root dependency install is needed. `index.cjs` is CommonJS. This package's validator requires its development dependencies, so install without omitting dev dependencies.

## Contents and supported cases

- `schema/ai-pet.schema.json`: portable Draft 2020-12 definitions. Reference a named definition via `urn:keepwork:ai-pet:unpublished:dev:v1#/$defs/selection` (and similarly for others). Schema IDs are identifiers, not endpoints. `$defs` is a library, not an envelope union; consumers must select the intended definition. Contract marker `ai-pet.dev.v1` is independent of package and product versions.
- `fixtures/positive.json`, `negative.json`: synthetic valid structures and invalid JSON-pointer mutations. A valid structure says nothing about authorization or real catalog rights. Paths/digests do not represent downloadable files.
- `fixtures/voice-lifecycle-scenarios.json`: shared Kotlin/Swift/JS-compatible event/checkpoint cases; see `fixtures/README.md`. `dev-lifecycle.cjs` is an offline reference model, not a native lifecycle implementation.
- `index.cjs`: shape checks, selection binding, capability intersection, request identity preservation, output fencing, deliberate resume checks, historical import candidate evaluation and usage identity checks. Functions throw bounded reason strings; they neither persist nor execute effects.

Account/home-region identity remains independent of locale or travel. Region/character IDs are opaque development identifiers, not a frozen production routing taxonomy. Selection binds official character/version and separate appearance/version. Production account and catalog adapters default to denial. Revoked/withdrawn entries cannot authorize new selections; historical attribution is not relabeled.

Capability responses permit additive fields and unknown capability names. Unknown or absent capabilities provide no authority; intersection chooses only explicitly shared versions. An older peer keeps ordinary supported text while unsupported voice remains unavailable. Capability names in fixtures are candidate names, not published service advertisements. Sensitive commands and migration records reject extra fields; incompatible command semantics require an explicitly negotiated contract. Generic response additions are never promoted into permissions.

Conversation commands preserve account, character, conversation, request and turn identity. Repeated append requests with unchanged identity/content return `inspect-existing-outcome`; this is a directive to consult the real request ledger, not a retry scheduler. Text cancellation is distinct from lease/capture teardown.

Voice outputs require exact account/region/character/conversation/request/turn/session plus lease and turn generations, active unexpired state, increasing sequence and no cancellation. Lease state, current time, sequence cursor and cancellation status must come from the trusted runtime/service adapter, not the output packet. Lease expiry/revocation is terminal (`ended`), with capture/playback off; a fresh explicit start and admission are required. Phone/competing-recorder/network interruptions instead pause a live session. Resume requires a paused session, matching device and pause revision, fresh deliberate intent, valid lease and all five independent native/service checks. The caller must atomically consume intent IDs and perform lifecycle transitions; this validator does not acquire a lease or start capture. Production takeover, watchdog deadlines, mute, session admission and usage exclusion require native/service implementation. New admissions never reuse revoked lease generations.

Migration accepts only bounded completed consumer transcript rows with supported source identity, immutable snapshot revision and independently resolved account/official-character mapping. The default exporter adapter fails closed. A real `migration(evidenceRef)` adapter must independently authenticate and return binding fields, `source`, `completedConsumerHistory`, and **immutable exact `messages` evidence**; it must not copy submitted envelope fields. Every eligible row must match the evidence by source ID, role, text, order, timestamp and digest. The digest is SHA-256 of UTF-8 `JSON.stringify([role,text,order,createdAtMs])`, with no whitespace (candidate JS-compatible JSON string serialization; canonical cross-language encoding must be agreed before service adoption). It is checked against the payload but is never ownership evidence. The fixture tests reject changed text retaining its digest, recomputed attacker digests, injected rows, wrong accounts/characters/sources, duplicate rows and changed imports.

Migration deduplication keys use account, home region, source format/version, installation, source conversation and source message, **not** batch ID or snapshot revision. Tombstones can target a message or `'*'` for the source conversation, take precedence over imported receipts, and suppress later snapshots. Deletion state and imported digest maps must be trusted and durably maintained by the service. Here evaluation is read-only; no data is imported/deleted and no inference is replayed. Real transactional import, authenticated receipt/cursor persistence, cross-installation canonical mapping, concurrent deletion reconciliation, source deletion propagation and provider retention remain external gates. A source adapter must normalize aliases across installations; these local source keys alone cannot identify two independent exports of one cloud record.

Entitlement/usage checks bind account, region, grant, allowance version, period, session and fence. `authorizeUsage` is **candidate identity validation only**: it returns a candidate reservation/settlement key after checking independent entitlement evidence and consumption bounds. It does not reserve allowance, validate a store transaction, grant trial/subscription rights, enforce concurrency, or persist a settlement. Repeated keys require a service-side atomic ledger that rejects changed payloads; distinct settlement IDs must not allow a reservation to be spent twice. Actual billing units are deliberately unavailable (`dev-unit-not-billable`). Pending/revoked/expired grants are rejected.

Asset manifests require seven poses (idle/happy/listening/thinking/speaking/sleeping/error), six locale labels (`zh-CN`, `en-US`, `es-ES`, `ko-KR`, `ja-JP`, `fr-FR`), integrity metadata, dimensions, normalized anchor, poster, timing, amplitude mouth mode and provenance/license references. References are not rights approval. No asset downloads or decoding occur; the asset adapter must verify actual bytes, safe extraction/decoding, dimensions and regional rights.

## Trust boundary and external decisions

`shape` validates structure only. No self-asserted `verified` flag is authority. All production trust adapters in `denyAdapters` reject by default; tests inject synthetic evidence, never live credentials. Adapter evidence and state inputs are trusted **only by the host's integration**, not because they match these schemas. Consumers must not expose these helper parameters as a client-controlled authorization API.

Canonical owners still must agree: login/refresh/revocation and stable region mapping; catalog eligibility/withdrawal/version and asset rights; supported exporter formats and immutable evidence; request/stream ordering and sync/deletion receipts; lease authority, expiry/watchdog, takeover and legacy-client fencing; native resume eligibility; purchase verification, trial/subscription periods, units and atomic reservation/settlement; durable deletion and provider/backup retention. No release gate is closed by these mocks.

Tool choices checked against primary docs on 2026-11-13: [JSON Schema validation](https://json-schema.org/draft/2020-12/json-schema-validation), [Ajv Draft 2020-12 support](https://ajv.js.org/json-schema.html#draft-2020-12), [Node test runner](https://nodejs.org/api/test.html). Repository design sources: `docs/ai-pet-implementation-spec.md`, `docs/ai-pet-cross-platform-plan.md`, `CONTEXT.md`.

## Slice 2: deterministic history and command journal

`history.cjs` exports `create(binding, epoch)`, `reduce(state, action)`, `createJournal(binding, epoch)`, `appendJournal(journal, action)` and `restoreJournal(serialized)`. The reducer returns new `{state, effects}` values without mutating its input; the journal helpers also return the next journal. Their formats are `ai-pet.dev.history.v1` and `ai-pet.dev.journal.v1`, independent of the existing wire candidate marker. They do not import any application code, access local history files, open sockets or run model inference. Existing contracts and 41 initial checks remain supported. The portable [history scenario format](fixtures/README.md#conversationhistory-scenarios-development-revision-1) documents every action and checkpoint; `fixtures/history-scenarios.json` can drive native harnesses later.

This slice separates draft text, queued commands, uncertain outcomes, accepted transcript rows, ordered cursor, cancellation fences, message/source tombstones and terminal conversation deletion. It tests duplicate/conflicting sequences, out-of-order recovery, immutable retry identity, stale result attempts, account/persona/activation isolation, late generated output after cancellation, deletion before/during imported batches, ordinary message deletion without migration metadata, atomic rejection, and serialized journal restart. Candidate imports are pre-authorized synthetic server events; `evaluateMigration` remains the separate fail-closed provenance check before a real adapter could construct them.

Persist the returned journal **successfully before** executing effects. `dispatch` records unknown outcome before exposing an append effect; crash/reload reconstructs state and discards effects. Unknown commands query their outcome; only an authoritative definitive absence can enable an explicit identity-preserving retry. Each dispatch increments an attempt fence, and query results must match it. A transport timeout or missing local receipt is never definitive absence. Production still needs a server-side idempotency ledger to cover in-flight requests and atomic receipt lookup.

Scope switches create a fresh journal/activation rather than relabel old records. The host chooses the authenticated account partition and a new activation epoch, stops old producers, and must prevent presentation of another account's loaded state. `restoreJournal` is a version-checked deterministic reconstruction function, **not authentication, a secure storage loader or authority to select its self-declared account**. Malformed actions/unsupported journal versions fail without a returned partial state. Do not hand untrusted files or real transcripts to this development helper.

Deletion removes visible rows and leaves durable-in-the-serialized-model suppression markers; source suppression requires a real mapping, never a fabricated source ID. A message-ID-only deletion cannot identify an as-yet-unmapped alias from another exporter. That mapping, authenticated server ordering and deletion convergence remain BC-03/05/06 dependencies. Conversation deletion is terminal; a new conversation needs a new identity. Selective clear/revision-cutoff semantics are intentionally not guessed.

**Durability/privacy limitations:** the journal is an in-memory, append-only synthetic action log capped at 10,000 actions, with JSON round-trip tests only. It has no file adapter, fsync, locking, encryption, integrity signature, compaction, backup handling, crash-atomic transaction or cross-device service. Historical journal actions can still contain deleted synthetic text; the current state projection scrubs pending command text on conversation deletion and mapped accepted-user command text on message deletion, but visible tombstone suppression does not erase log bytes. Production retention requires authenticated compacted snapshots and verified erasure of historical journal/storage copies. Do not persist real user text through this development package. No actual cross-device convergence, deletion from providers/backups, or production retry safety is proven by these tests.

## Slice 3: compact checkpoints and host-controlled reactivation

Stable QA/native handoff: `require('./checkpoint.cjs')` exports:

```js
const checkpoint = compactCheckpoint(state); // plain JSON value; no actions/log
const { state: resumed, effects } = restoreCheckpoint(JSON.stringify(checkpoint), {
  expectedBinding: authenticatedHostBinding, // all five binding fields
  freshEpoch: hostIssuedNewActivation
}); // effects is always []
```

The host arguments must be supplied independently of the stored value. Never copy a saved binding or activation to satisfy them. This is a development codec, not a login or authorization implementation: the host still authenticates the account and selects its storage partition. On load, all five binding fields must match, and the new epoch must differ from every activation recorded by this checkpoint lineage. Each subsequent checkpoint retains prior activations. The host must additionally ensure global freshness across separate/stale checkpoint branches; the codec cannot discover a previously used epoch omitted by a rolled-back file. Old callbacks fail against the resumed state's new epoch, including switching away and back to the same account/persona.

`schema/history-checkpoint.schema.json` strictly defines `ai-pet.dev.checkpoint.v1`: no additional fields; arrays of at most 10,000 elements; strings/IDs bounded; total encoded input/output at most 8 MiB. Cursor count must equal retained event-digest count, gap must match recovery target, request/message/source identities must be unique, command status/attempt/text must be consistent, and visible rows must not conflict with tombstones or command bindings. Malformed, unsupported, mismatched and inconsistent values fail before any restored state is returned. Unknown/retry command IDs, original text/turn/attempt, cancellation, message/source tombstones and gap target survive; loading never submits, retries or emits inference effects. Continue using the existing pure `reduce` on the restored state and checkpoint again as needed.

Compaction discards **all raw historical actions**, not replay fences. Every accepted sequence digest is retained in order, so both equivalent duplicates and conflicting reuse remain detectable after restart. No digest window/pruning is guessed: reaching the schema/byte/activation capacity fails closed and requires an explicitly designed next version or service-supported fence. Digests can still reveal equality or permit guesses of low-entropy text; they are not secure erasure. `integritySha256` hashes the canonical payload (excluding itself), for accidental corruption detection only. Canonicalization recursively sorts object keys in JavaScript order, preserves array order, then uses UTF-8 `JSON.stringify`; native candidates must reproduce that encoding or use a later agreed canonical codec. The plain digest is neither a MAC nor an authenticity or rollback guarantee. A coherently forged checkpoint with a recomputed digest cannot be distinguished from trusted state; storage integrity/authority remains external.

Deletion fixes in this slice scrub command plaintext for every user row actually removed by a known source alias, not just a matching message ID. The removed canonical IDs are also tombstoned. A late independently trusted user row that matches an existing tombstone supplies the request/source mapping needed to scrub its pending command and suppress subsequent source aliases. Before that mapping exists, a message-ID-only tombstone cannot safely identify which unknown command to scrub; checkpointing preserves that unknown command rather than inventing ownership. Deleting the whole conversation always scrubs every command payload. A later supported service adapter must supply canonical mappings to meet the complete deletion guarantee.

The original `createJournal`/`appendJournal`/`restoreJournal` APIs and `ai-pet.dev.journal.v1` fixture behavior remain unchanged. `restoreJournal` still reconstructs its stored activation and is explicitly **not** the host-reactivation entry point. To migrate synthetic journals, reconstruct them in a trusted context, compact their state, then call `restoreCheckpoint` with independent host binding/fresh activation. There is no silent journal-version migration and no new disk adapter.

Deleting bytes from prior journals, temporary files, snapshots, backups, filesystem blocks and external services remains unimplemented. The returned compact JSON omits known deleted plaintext/obsolete actions, but creating that JSON does not securely erase old copies or make a crash-atomic replacement. Tests use synthetic values only. Portable checkpoint cases live in `fixtures/checkpoint-scenarios.json`; their execution protocol is documented in `fixtures/README.md`.
