# 从规则到原生游戏作品

Paracraft 是游戏引擎。以玩家的输入、世界状态和可观察结果为中心，把场景、
角色、电影、代码方块和原生机关组合起来。模板是实现部件，不是可制作玩法的边界。
无需先读全部美术指南；先证明最不确定的引擎能力，再完成一小段真实可玩的闭环。

## 规则变成实现

从用户描述提取：玩家控制谁、输入是什么、有效范围、如何反馈、胜负或结束条件、
重玩方式。缺少非关键细节时选择简单默认值并写进作品说明；不能用默认值改变用户
明确的规则。纯动画没有胜负，单次交互也不必强行加入计分和回合框架。

例如“护送机器人穿过仓库，拿到钥匙开门”至少有：可到达的路线、机器人跟随、
钥匙唯一领取、实际阻挡的门、抵达检测、失败/脱离策略，以及相应角色反馈。
先用短路线和少量角色跑通这个链条，再加美术、支线或更多关卡。

把实现分到有实际作用的原生部件，而不是为每条规则新造一套框架：

| 职责 | 原生表示 | 需要证明的结果 |
|---|---|---|
| 地图与可通行区域 | 原生方块、地形、门、碰撞体 | 尺度合理；起点到目标可达；视觉开门和碰撞解除一致 |
| 角色/道具 | MovieClip 演员、已验证模型、有限克隆 | 角色可见可识别；名称唯一；实例独立数据 |
| 规则 | 控制器 CodeBlock 的状态及短处理器 | 合法输入才改变状态；结束、复位、掉电一致 |
| 输入 | 点击/按键/距离/接触/机关信号 | 原生输入链真实生效；按钮有明确语义 |
| 表演 | 电影轨道、角色动作、声音、对话 | 事件触发正确片段；中断/重开恢复；不抢移动通道 |
| 玩家反馈 | `say`、原生 UI、灯光/颜色/动作 | 当前目标、进度、失败原因与重玩入口看得懂 |
| 生命周期 | 启动链、轮次、清理、保存的原生对象 | 可以再次启动；没有旧克隆、旧回调或资源泄漏 |

实现接口先读引擎 `creation.md` / `code-block.md`；运行语义在
[code-blocks.md](code-blocks.md)，具体组合在 [codeblock-patterns.md](codeblock-patterns.md)。
需要物理电路读 [circuits.md](circuits.md)，动画/分镜分别读
[animation.md](animation.md) / [filmmaking.md](filmmaking.md)。不把脚本位移称为
寻路，也不把本地共享 `_G` 称为多人同步。能力不支持时指出具体缺口，选择可验证
的替代实现；不能承诺任意规则都已经通过验证。

## 状态与角色的所有权

简单玩法可以一个代码块。多个角色改变同一局规则时，让一个控制器拥有规则状态，
输入演员只提出请求，视图演员读取已提交结果。一个位置、一个电影通道或一个对话框
只由当前明确的 owner 写入。

- 多次输入必须逐个处理时用**有上限的队列**；重开按钮通常可以合并为一个请求。
  回调不可通过长 `wait` 来排队；同类原生事件可能停止上次回调。
- 队列元素携带实例 ID 和 epoch。消费时再校验阶段、轮次、范围、占用及冷却。
  不只在入队时检查，因为消费前可能已经结束或重开。
- 克隆的 ID/epoch 放 actor value；顶层 `local` 闭包在克隆间共享。规则状态与显示
  分离：棋盘数据先落子，演员再变色；不是靠“某角色是什么颜色”裁决胜负。
- 结束后是否保留视图由玩法决定：棋盘保留最终局面，收集品通常清掉；重置和停止
  则清理本模块实例。不要把一种示例的清理时机复制到所有玩法。
- 初始化先建立监听者/输入模板，再启动控制器；缺少依赖显示 `not_ready`。
  演员存在仅说明已创建，不总等于事件注册完成；复杂模块用显式 ready/ack 或
  可观察的初始化状态，避免依靠固定短延时保证成功。

## 时间、移动与演出

规则钟由同一个控制器使用 `getTimer()` 的秒与绝对 deadline；它是代码块本地
启动时钟，不能拿输入角色的 `getTimer()` 与控制器的 deadline 比较。明确临界顺序：截止时收到的点击是
拒绝还是有效，死亡与到达同一帧谁优先。处理输入时也校验截止时间，不能等下一次
tick 才禁止计分。暂停需要扣除暂停时长或平移 deadline。

运动用时间差或绝对进度，不用“每帧前进一点”决定速度。定时事件选择明确策略：
固定日程需要有界补处理；交互提示后给玩家完整反应时间则可以从当前时刻重设期限。
不能无界追赶卡顿期间的每一帧。高速碰撞需要扫掠/细分或原生物理，不靠终点距离。

动画和行为是两层。胜利后 `play(0,1000)` 使用电影毫秒，不是秒；编写轨道时
`scene:keyframe(..., 1, ...)` 使用秒。先给电影该通道的控制权，重开时停止播放、
恢复片段起点和出生位置，再恢复行为移动。不能同时让巡逻循环覆盖电影位置。
代码 API `getPos` 是方块单位；原生 `CodeActor:GetPosition()` 是引擎世界单位，
验收时转换后再比较，不能直接混算。

## 先跑规则，再检查玩家体验

选择能区分错误实现的短轨迹，避免仅断言内部变量曾被设置：

| 作品 | 正向轨迹 | 应被拒绝/恢复的轨迹 |
|---|---|---|
| 顺序机关 | 2→1→3 后播放解锁 | 错序；重复；解锁动画中重开；再次解锁不漂移 |
| 回合棋盘 | 合法交替落子产生横/竖/斜胜利 | 已占格；边界串行误连；终局输入；和局；复位 |
| 避障/竞速 | 原生输入改变车道/位置，抵达终点 | 接触扣血；持续接触冷却；越界；自然失败；重开 |
| 分支任务 | 拒绝/接受→条件达成→完成 | 未接受就领奖；取消；重复领奖；中途退出 |
| 交互演出 | 输入→连续播放→归还控制 | 快速重复输入；中途取消；恢复相机/角色/UI |

查看真实阶段、角色数量、变换、原生输出和时间线；不能直接写 `won` 后宣布通关。
`Actor:OnClick` 能检验引擎事件，仍不等于屏幕拾取测试。用不同视角检查可见性，
至少有一张**运行中、可辨认输入与反馈**的视图；停止后只剩控制块的远景无法证明
玩家能玩。按需补真实输入体验，不把没测过的部分列为通过。

交付时给出实际入口、操作、胜负/结束和重玩方式，保留源码、角色与电影可编辑。
记录保存状态；原生保存和重开按授权范围执行。自建专用验证世界可以用于保存验收，
不要把测试需求扩展成保存或切换用户已有世界。

## 可运行的组合实验

[engine-games.lua](../examples/engine-games.lua) 在同一世界放置三个独立作品：顺序
机关与位置动画、4×4 三连棋、三车道计时避障。每个作品有 host 与 inputs 两个
物理站：先开启 inputs 拉杆，再开启 host，点击主持人开始/重开。此例是规则与
原生装配实验，用简易玩具角色，非最终美术标准。

避障是**抽象车道判定**，危险车道每波显示约一秒；不是实体碰撞/寻路示例。
棋盘结束后保留棋子颜色；停止主持人清理输入克隆。代码默认不自动启动、不保存
原生世界。场景/角色/代码名字以 scene name 隔离；第二份安装需要不同名称、资产
路径和场地，修改已有作品则读取并保护性更新原生源码。

现成实验用 `template_info {template:"engine_games"}` → `run_template`，携带返回
hash 和正常世界/聊天/请求身份，可避免把整段 Lua 复制到调用里；需要留生成器时
传 `saveSource:true`。`interactions` 分类可发现两个交互模板。新玩法仍应改规则和
美术，不要求复制三游戏展台布局。旧网关的 `unknown_template` 按
[connection.md](connection.md) 检查服务版本或使用已读源码，不要重试创建来刷新目录。

规则迁移应改变状态关系：换目标颜色不算新玩法验证。比如把顺序机关改成任意
顺序全点亮，必须用 3→2→1、重复按钮和部分完成验证；改 N 连子需要测试盘边和
和局；把车道判定换成实体障碍要重新验证碰撞链。

优化 skill 时把实验报告放开发/测试证据中，只把可复用结论写回指南。连续不同
规则迁移不再暴露高收益共性问题，且正向、异常、停止/复位、视觉反馈和授权范围内
的持久化已得到证据时，可以结束本轮；这不代表所有可能玩法或平台都已验证。
